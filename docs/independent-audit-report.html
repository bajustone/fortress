High Severity: Privilege escalation / scope bypass

H1 — API-key scopes are stored, returned to clients, and never enforced

What the docs promise

The api-key plugin advertises "scoped, hashed API keys" with "per-key permission scopes" and accepts a scopes: string[] array on key creation. Keys are intended to act as narrowing credentials for an owning subject.

What actually happens

The principal resolver explicitly drops the scope array before handing the request off to the auth pipeline. RBAC then checks permissions against the subject's full IAM grants, ignoring the narrower scopes attached to the key. A key created with scopes: ['report:read'] on a subject that holds report:delete can delete reports.

Proof

src/plugins/api-key/index.ts:186-198async resolvePrincipal(request: Request, ctx: PluginContext): Promise<{ subject: Subject; scopes?: string[] | null } | null> {
  const auth = request.headers.get('authorization') ?? '';
  const fromAuth = auth.startsWith('ApiKey ') ? auth.slice(7).trim() : null;
  const fromHeader = !fromAuth ? request.headers.get('x-api-key') : null;
  const key = fromAuth ?? fromHeader;
  if (!key)
    return null;
  const resolved = await resolveApiKey(ctx.db, key);
  if (!resolved)
    return null;
  return { subject: resolved.subject };   // ← scopes discarded here
}
src/core/http/principal.ts:34-49export async function tryPluginPrincipal(
  fortress: Fortress, request: Request,

How to fix

  1. Thread scopes through the principal type: 
    src/core/http/principal.ts (proposed)export interface ResolvedPrincipal {
  subject: Subject;
  claims?: TokenClaims;
  scopes?: string[] | null;   // null = unscoped (full subject permissions)
}
  2. Return them from the api-key plugin's resolvePrincipal: 
    src/plugins/api-key/index.ts (proposed)return { subject: resolved.subject, scopes: resolved.scopes };
  3. Intersect at the permission-check boundary. Add a helper used by both RBAC middleware and iam.checkPermission: 
    src/core/iam/permission-evaluator.ts (proposed)function withinScope(scopes: string[] | null | undefined, perm: { resource: string; action: string }): boolean {
  if (!scopes) return true;                  // unscoped key = subject's full perms
  return scopes.some(s =>
    s === '*' ||
    s === `${perm.resource}:*` ||
    s === `${perm.resource}:${perm.action}`
  );
}
  4. Add a regression test: create a key with scopes: ['report:read'] on a subject that holds report:delete; assert the key cannot delete.
High Severity: Privilege escalation via built-in endpoint

H2 — Built-in POST /auth/impersonate endpoint has no permission gate

What the docs promise

Both the OpenAPI description on the route and the JSDoc on the service method state: "Requires fortress:impersonate permission." The implication is that the route enforces it.

What actually happens

The route declaration only sets .security('bearer') — any authenticated user can call it. Enforcement is delegated to the caller via a JSDoc note. The schema-builder has a .permission(resource, action) method (used elsewhere) that would wire the RBAC middleware; it is simply not called here.

Proof

  .response(200, 'Impersonation token issued', authRef('AuthResponse'))
  .response(401, 'Not authenticated', authRef('ErrorResponse'))
  .response(404, 'Target user not found', authRef('ErrorResponse'))
  .handler('impersonate')
  .build() as AuthEndpointsMap['impersonate'],

src/core/auth/auth-service.ts:92-98/**

The builder is fully capable of declaring the permission — other endpoints use it:

How to fix

src/core/auth/auth-endpoints.ts (proposed)impersonate: endpoint('POST', '/auth/impersonate')

  .body(...)
  .handler('impersonate')

Then in impersonate service: switch the JSDoc note from "Caller must verify..." to "Permission enforced by route metadata", and harden programmatic callers by also calling iam.checkPermission(adminUserId, 'fortress', 'impersonate') at the top of the service method as a defense-in-depth pre-condition.

Also: ship a regression test that posts to /auth/impersonate with a bearer token whose subject lacks the permission and asserts 403.

High Severity: Race condition — duplicate valid refresh tokens / family-revoke evasion

H3 — Refresh-token rotation is not atomic (both core auth and OAuth)

What the docs promise

The CHANGELOG advertises "RFC 9700 §2.2.2 replay detection" and the auth flow is documented as "rotate on every refresh, detect reuse and revoke the whole family." For that defense to be sound, the lookup-then-revoke-then-mint sequence must be atomic relative to other refresh attempts on the same token.

What actually happens (core)

Refresh consists of four discrete adapter calls in series, with no transaction or row lock, and the revocation is an unconditional UPDATE WHERE id = ? rather than a conditional UPDATE WHERE id = ? AND is_revoked = false:

src/core/auth/auth-service.ts:347-470 (abridged)async refresh(refreshToken: string, meta?: RequestMeta): Promise<AuthTokenPair> {
  const tokenHash = await hashToken(refreshToken);
  const stored = await adapter.findRefreshTokenByHash(tokenHash);          // 1. read
  if (!stored)                       throw Errors.unauthorized('Invalid refresh token');
  if (stored.isRevoked) { ...family revoke + throw reuse... }              // 2. check
  if (stored.expiresAt < new Date()) throw Errors.unauthorized('expired');

  // ... fingerprint check ...

  await db.update({                                                        // 3. revoke
    model: 'refresh_token',
    where: [{ field: 'id', operator: '=', value: stored.id }],
    data: { isRevoked: true },
  });

  // ... user lookup ...

  await db.create({                                                        // 4. mint new
    model: 'refresh_token',
    data: { userId: stored.userId, tokenHash: newToken.hash,
            tokenFamily: stored.tokenFamily, isRevoked: false, ... },
  });
  // returns new pair
}

Failure scenario

  1. Two concurrent refreshes A and B arrive with the same valid token.
  2. Both execute step 1 and read isRevoked = false.
  3. Both pass step 2 (no reuse detected).
  4. Both execute step 3 — idempotent, both succeed.
  5. Both execute step 4 — two new valid refresh tokens issued in the same family.

The replay-detection mechanism never fires because no second call ever sees isRevoked = true for the original token. The family now has two unrevoked descendants, the attacker wins.

What actually happens (OAuth)

Same shape, same defect:

src/plugins/oauth/index.ts:758-839 (abridged)const tokenHash = await hashToken(params.refreshToken);
const record = await ctx.db.findOne<RefreshTokenRecord>({                  // 1. read
  model: 'oauth_refresh_token',
  where: [{ field: 'token', operator: '=', value: tokenHash }],
});
if (!record)                       throw Errors.oauth('invalid_grant', '...');
if (record.usedAt) { ...family delete + throw reuse... }                   // 2. check
// ...
await ctx.db.update({                                                      // 3. mark used
  model: 'oauth_refresh_token',
  where: [{ field: 'id', operator: '=', value: record.id }],
  data: { usedAt: new Date() },
});
// ... mint new access & refresh tokens ...                                // 4. mint

How to fix

Two complementary changes; either is sufficient, both is robust:

  1. Conditional update — minimal change, works on any backend: 
    src/core/auth/auth-service.ts (proposed)// Replace the "find then update by id" pair with an atomic CAS.
const claimed = await adapter.claimRefreshToken({ tokenHash });
// Returns the row only if it was previously is_revoked=false AND atomically
// flipped it to true. Implemented as:
//   UPDATE refresh_token
//   SET is_revoked = true
//   WHERE token_hash = $1 AND is_revoked = false
//   RETURNING *;
// On Postgres & SQLite both, RETURNING gives us exactly one row to a
// single winner; losers get null and take the reuse branch.
if (!claimed) {
  // Either token never existed OR another concurrent refresh already
  // consumed it — treat as reuse and burn the family.
  const stored = await adapter.findRefreshTokenByHash(tokenHash);
  if (stored) await revokeFamily(stored.tokenFamily);
  throw Errors.tokenReuse();
}
  2. Transactional wrap — for the multi-step branches (fingerprint mode, user lookup, mint): 
    src/core/auth/auth-service.ts (proposed)return db.transaction(async tx => {
  const claimed = await tx.update({
    model: 'refresh_token',
    where: [
      { field: 'tokenHash', operator: '=', value: tokenHash },
      { field: 'isRevoked', operator: '=', value: false },
    ],
    data: { isRevoked: true },
    returning: true,
  });
  if (!claimed.length) { ...reuse path... }
  // ... mint & insert new token within the same tx ...
});

Apply the same pattern to src/plugins/oauth/index.ts refreshTokenGrant. Add a regression test that fires N parallel refreshes on the same token and asserts exactly one succeeds, the other N-1 trigger token_reuse and the family ends up fully revoked.

Medium Severity: Silent semantic collapse — DENY rules unrepresentable

M1 — findOrCreatePermission keys only on (resource, action), silently discarding effect and conditions

What the docs promise

The Permission type carries effect: 'ALLOW' | 'DENY' and conditions (CEL-like predicates). The permission-evaluator honours both. So a caller can reasonably expect createPermission({ resource: 'doc', action: 'read', effect: 'DENY' }) to create a deny rule.

What actually happens

The find branch ignores effect and conditions: if a row with the same (resource, action) exists with any effect/conditions, it's returned and the caller's intent is silently dropped.

src/core/internal-adapter.ts:262-284async findOrCreatePermission(input: PermissionInput): Promise<Permission> {
  const existing = await db.findOne<Permission>({
    model: 'permission',
    where: [
      { field: 'resource', operator: '=', value: input.resource },
      { field: 'action',   operator: '=', value: input.action  },
      // ← effect and conditions are NOT part of the lookup key
    ],
  });

  if (existing)
    return existing;     // ← caller's effect/conditions silently dropped

  return db.create<Permission>({
    model: 'permission',
    data: {
      resource: input.resource,
      action: input.action,
      effect: input.effect ?? 'ALLOW',
      conditions: input.conditions ? JSON.stringify(input.conditions) : null,
      description: `${input.action} ${input.resource}`,
    },
  });
}

Failure scenarios

  • An ALLOW row exists for doc:read. A later bindPermissionToUser(u, { resource: 'doc', action: 'read', effect: 'DENY' }) calls findOrCreatePermission, gets the ALLOW row, and binds that to the user — granting read instead of denying it.
  • Two callers want doc:read conditioned differently (e.g. tenantId == 'x' vs tenantId == 'y'); the second silently inherits the first's condition.

How to fix

Pick one of two consistent semantics and document it:

  1. Make permission identity include effect & conditions: 
    src/core/internal-adapter.ts (proposed)const conditionsKey = input.conditions ? JSON.stringify(input.conditions) : null;
const existing = await db.findOne<Permission>({
  model: 'permission',
  where: [
    { field: 'resource',   operator: '=', value: input.resource },
    { field: 'action',     operator: '=', value: input.action },
    { field: 'effect',     operator: '=', value: input.effect ?? 'ALLOW' },
    { field: 'conditions', operator: '=', value: conditionsKey },
  ],
});
    Couple with a Drizzle migration adding UNIQUE (resource, action, effect, conditions) on fortress_permission.
  2. Or reject the ambiguous call: if existing is found and its effect/conditions differ from input, throw Errors.conflict('permission row already exists with different effect/conditions') — forces the caller to pick.
Medium Severity: Data integrity — duplicate bindings; idempotency violation

M2 — No uniqueness constraint or dedup check on role/permission bindings

What the docs promise

"Bind role to subject" is implicitly idempotent in a typical IAM mental model — calling it twice with the same arguments should be a no-op, not a doubling.

What actually happens

The schema has no UNIQUE constraint on the natural identity tuple, and the service unconditionally INSERTs. Duplicates accumulate; the evaluator's dedup happens later in memory, but listRoles-style admin reads return duplicates, audit logs become misleading, and storage grows monotonically. Worse, the seed-script workaround that TDMP shipped pre-checks bindings precisely because of this.

src/drizzle/schema.ts (role_binding shape)const roleBindings = sqliteTable('fortress_role_binding', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  roleId: integer('role_id').notNull().references(() => roles.id, { onDelete: 'cascade' }),
  subjectType: text('subject_type').notNull(),
  subjectId: integer('subject_id').notNull(),
  tenantId: text('tenant_id'),
  // ← no UNIQUE(roleId, subjectType, subjectId, tenantId)
});

How to fix

  1. Add UNIQUE constraints in src/drizzle/schema.ts for both backends: 
    src/drizzle/schema.ts (proposed)const roleBindings = sqliteTable('fortress_role_binding', {
  /* ... fields ... */
}, t => ({
  uniqBinding: uniqueIndex('uniq_role_binding')
    .on(t.roleId, t.subjectType, t.subjectId, t.tenantId),
}));
    Same for direct_permission_binding and group_user.
  2. Use an ON CONFLICT DO NOTHING (Postgres) / INSERT OR IGNORE (SQLite) wrapper, or pre-check in the service: 
    src/core/iam/iam-service.ts (proposed)const existing = await db.findOne({ model: 'role_binding', where: [...] });
if (existing) return;
await db.create({ model: 'role_binding', data: { ... } });
  3. Ship a migration that DELETEs the surplus duplicate rows before the UNIQUE constraint is applied.
Medium Severity: Latent performance — N×queries per permission check at scale

M3 — Drizzle adapter never implements rawQuery, so the optimized IAM path is dead code for Drizzle users

What the code promises

The internal adapter ships an "optimized path: single JOIN query when rawQuery is available" specifically to collapse permission resolution from N round-trips to one:

src/core/internal-adapter.ts:115-153// Optimized path: single JOIN query when rawQuery is available
if (db.rawQuery) {
  // ... builds a JOIN across role_binding / role_permission / permission ...
  const rows = await db.rawQuery<Permission>(sql, params);
  return rows;
}
// Fallback path: N findMany calls below ...

What actually happens

The default Drizzle adapter — the one most users mount — does not export rawQuery:

$ rg -c "rawQuery" src/drizzle/adapter.ts0

Every permission check therefore falls into the fallback path: a sequence of findMany calls to fetch bindings → role_permissions → permissions, multiplied by group memberships. With moderate IAM cardinality this is 5–10× more queries than necessary per authorized request. There is no error and no warning, so no one notices until traffic hits a wall.

How to fix

src/drizzle/adapter.ts (proposed, Postgres)return {
  // ... existing methods ...
  dialect,
  async rawQuery<T>(sqlText: string, params?: unknown[]): Promise<T[]> {
    if (dialect !== 'pg') throw new Error('rawQuery only implemented on pg');
    // drizzle-orm/postgres-js exposes execute() with sql.raw
    const result = await db.execute(sql.raw(sqlText, params ?? []));
    return result.rows as T[];
  },
};

Add the equivalent SQLite implementation (better-sqlite3 / bun:sqlite both expose a prepare().all(...params) path). Add a smoke test asserting db.rawQuery is defined after drizzleAdapter() construction so the dead-code branch can't silently re-appear.

Low Severity: Supply-chain / trust signal — version & doc drift

L1 — Version and maturity signals are inconsistent across package.json, jsr.json, and SECURITY.md; published package excludes referenced docs

Proof

package.json"name": "@bajustone/fortress",
"version": "0.1.1",

"version": "0.0.35",                  ← 6 minor versions behind npm
"publish": {
  "exclude": [
    "examples",                       ← README links into examples/
    "docs",                           ← README + CHANGELOG link into docs/
    "scripts",
    ...
  ]
}
SECURITY.md## Supported Versions

| Version | Supported |
|---------|-----------|
| 0.0.x   | Yes       |                ← does not list 0.1.x as supported

Why it matters

A consumer reading SECURITY.md today would conclude that 0.1.1 is unsupported and that no version receives patches. A JSR consumer is installing a version six minors behind npm with no signal that they're drifting. Anyone clicking docs/... links from the JSR-installed README is hitting a 404 because docs/ is excluded from the published tarball.

How to fix

  1. Add a release script that bumps package.json, jsr.json, and the SECURITY.md table in a single commit, and have CI fail the publish if the three versions diverge.
  2. Update SECURITY.md to: 
    SECURITY.md (proposed)| Version | Supported           |
|---------|---------------------|
| 0.1.x   | Yes                 |
| 0.0.x   | No (pre-0.1; please upgrade) |

Note: pre-1.0 — breaking changes may ship in any minor. Pin to a minor.
  3. Either include docs/ and examples/ in the JSR publish, or rewrite the README links that point into those directories to absolute GitHub URLs at the release tag.

What's good

The architecture and ergonomics genuinely deserve their A-: the unified plugin model, endpoint-as-data declarations, subject polymorphism (USER / SERVICE_ACCOUNT / GROUP), pluggable observers, OTel spans across the adapter, and the OAuth/OIDC compliance pass shipped in 0.1.0 are all above the bar for the category. The defects above are concentrated at the boundaries — where the principal meets RBAC, where the auth pipeline meets the database, where the published artifact meets the consumer — not in the core model. Each one has a small, surgical fix.

Final position

Fortress is a credible foundation that needs three boundary fixes before it should be relied on as the sole auth/IAM layer of a multi-tenant service. The independent audit confirms the TDMP review's findings without exception. If the three P0s land, the C+ on auth-correctness flips to a B+/A- on the same rubric; the remaining items are quality-of-life and supply-chain hygiene.
