Fortress — Independent Code Review

Review date: 2026-06-05 · Package: @bajustone/fortress@0.1.1 · Reviewer: Claude (independent pass) · Method: five focused subsystem reviews, every headline finding re-verified against source

Verdict: Architecturally strong and above-average for an auth library — but not production-ready. This review found three Critical and eight High issues. Several items the roadmap marks "Done" / "Mostly done" rest on foundations that do not hold (SQLite transactions don't isolate; the OAuth authorization-code exchange is racy). Three High-severity issues — cross-request data-isolation bypass, OAuth consent-flow IDOR, and no default CSRF — are absent from the roadmap entirely.

TL;DR

Fortress is genuinely well-built. The architecture is clean, default-deny is real and fails closed, password hashing is correct (Argon2id), the OAuth refresh-rotation path uses a proper transactional compare-and-swap with reuse detection, redirect-URI matching is exact, and secret comparisons are timing-safe.

But the roadmap is too optimistic about what is "done." This review confirmed the one Critical the roadmap already flags (tenancy SQL injection) plus four more Critical/High issues it does not account for:

  • The refresh-rotation atomicity marked "Mostly done" is unsound on the default SQLite adapter — the transaction wrapper doesn't isolate.
  • The OAuth work is strong on refresh rotation, but the authorization-code exchange itself is racy — a separate path the roadmap doesn't mention.
  • Two cross-request state-leak bugs (data-isolation bypass globals; OAuth consent-flow IDOR) are not on the roadmap at all.
  • CSRF is not wired into the pipeline by default, and the SvelteKit adapter actively disables SvelteKit's own CSRF with no replacement.

Bottom line: Do not ship as a production auth library yet. Treat the tenancy plugin as unsafe to enable until fixed; gate tenancy + data-isolation behind an "experimental / not production-ready" flag and fix the Critical items before any 1.0 claim.

1. Must-fix before any production / 1.0 claim

CriticalC1 + C2Tenancy SQL identifier injection

Tenant codes & tax IDs are interpolated raw into SQL

The roadmap already flags this, and it is real and Critical. tenantCode comes verbatim from the X-Tenant-Code request header and taxId from caller input; both are concatenated into raw SQL with no validation or quoting:

src/plugins/tenancy/index.ts:108, 116, 174-175const schemaName = `${schemaPrefix}${tenantCode}`;            // header-derived
await adapter.rawQuery(`SET LOCAL search_path TO ${schemaName}, public`);
// ...
await ctx.db.rawQuery(`CREATE SCHEMA IF NOT EXISTS ${schemaPrefix}${data.taxId}`);

Beyond the injection there is a functional bug that exposes how untested these paths are: the project's own test tax IDs (acme-001, beta-001) contain a hyphen, so tenant_acme-001 is not a valid unquoted identifier — CREATE SCHEMA would be a syntax error. The feature can't run against its own sample data.

Fix

Never interpolate identifiers. Derive the schema from the authenticated numeric tenant id (always safe), validate against ^[a-z_][a-z0-9_]{0,62}$, and use set_config('search_path', $1, true) with a bound value inside a transaction.

CriticalC3SQLite transaction wrapper doesn't isolate

The "atomic rotation" guarantee fails on the default dialect

The roadmap marks core and OAuth refresh rotation "Mostly done" on the strength of "transaction + conditional update." But on the default dialect (dialect defaults to 'sqlite'), the wrapper hands the callback the same shared adapter and opens a deferred BEGIN:

src/drizzle/adapter.ts:300-315if (dialect === 'sqlite') {
  (drizzle as any).run(sql`BEGIN`);
  try { const result = await fn(self); (drizzle as any).run(sql`COMMIT`); ... }
  catch (error) { (drizzle as any).run(sql`ROLLBACK`); throw error; }
}

fn(self) — not a tx-scoped adapter — and a plain BEGIN (not BEGIN IMMEDIATE). Because the callback awaits, a second concurrent refresh can issue BEGIN on the same connection ("cannot start a transaction within a transaction"), and one path's COMMIT/ROLLBACK closes the other's transaction. The compare-and-swap the whole reuse-detection design depends on is therefore not atomic on SQLite. The Postgres branch (native drizzle.transaction + buildAdapter(tx)) is correct.

Fix

For SQLite use BEGIN IMMEDIATE on a connection that cannot interleave mid-transaction (better-sqlite3 is synchronous — don't await foreign async work inside), or pass a genuinely tx-scoped adapter. At minimum, document that the rotation/reuse guarantees require Postgres.

HighH1OAuth authorization-code exchange is racy

The code is not single-use under concurrency

Distinct from the refresh path the roadmap praises. exchangeCode reads the code, checks if (authCode.usedAt), then unconditionally marks it used — no usedAt IS NULL guard, no transaction:

src/plugins/oauth/index.ts:607-643if (authCode.usedAt) throw Errors.oauth('invalid_grant', 'Authorization code already used');
// ...
await ctx.db.update({ model: 'oauth_authorization_code',
  where: [{ field: 'id', operator: '=', value: authCode.id }], data: { usedAt: new Date() } });

Two concurrent requests with the same code both pass the check and both mint tokens (RFC 6749 §4.1.2 / §10.5 require strict single-use). The refresh path ~200 lines later does this correctly — mirror it. Ideally, revoke tokens issued from a code on detected reuse.

2. High — cross-request leaks, CSRF, OAuth gaps

HighH4data-isolation bypass is global, not per-request
src/plugins/data-isolation/index.ts:30-31, 58, 104const bypassedScopes = new Set<string>();
let bypassAll = false;
// ...
async scopeRules(...) { if (bypassAll) return null; /* ... */ }
async unscoped(fn) { bypassAll = true; try { return await fn(); } finally { bypassAll = false; } }

bypassAll and bypassedScopes are module-level and mutated by unscoped() / withoutScope(). In any concurrent server, if request A enters unscoped() and awaits, request B's scopeRules runs with bypassAll === true and silently loses row-level isolation — a real cross-tenant/cross-user data-leak primitive.

Fix

Use AsyncLocalStorage to hold per-request bypass state.

HighH6OAuth consent-flow IDOR

oauth_pending_flow has no userId and is keyed by a sequential serial. handleGetFlow (gated only by security:['bearer']) returns another user's state — the relying party's CSRF token — enabling OAuth CSRF; handleApproveFlow/handleDenyFlow operate on arbitrary in-flight flows.

Fix

Add a userId column, bind it at consent, verify ownership in all three handlers (404 on mismatch), and use an opaque random flow id instead of serial.

HighH3 + H2Tenancy trusts the header & fails open

H3: Even after the injection fix, the per-request wrapAdapter path selects the schema from X-Tenant-Code and never checks the caller is a member of that tenant (switchTenant does check; the request path doesn't). Any authenticated user can target any tenant's schema. Derive tenant from the verified JWT claim or validate membership.

H2: SET LOCAL only lives for the current transaction; issued as its own autocommit statement and followed by a separate CRUD call (possibly on a different pooled connection), it's discarded — queries run against public. Isolation fails open silently. Run the switch and the query in one transaction, or pin a connection per request.

HighH5CSRF not enforced by default

mountFortress / createSvelteKitHandle route straight into handleRequest, which has no CSRF check. createCsrfMiddleware exists but is never wired in. SvelteKit's handle returns before resolve(), deliberately skipping SvelteKit's origin CSRF with no replacement (its own comment admits this). Cookie-authed POST routes (/auth/logout, /auth/refresh, /oauth/flows/:id/approve, impersonate) are cross-site reachable, defended only by SameSite=lax.

Fix

Apply origin / custom-header CSRF inside the pipeline for unsafe methods on cookie-auth routes by default.

HighH7 + H8PKCE enforcement gap & registration enumeration

H7: PKCE is enforced only in the opt-in authorize endpoint, not in createAuthorizationCode (reachable via the programmatic/consent path). A code minted with no challenge then skips verification entirely at exchange (if (authCode.codeChallenge && ...)). Enforce challenge presence in createAuthorizationCode for public clients, and at exchange treat a missing challenge on a public-client code as invalid_grant.

H8: createUser throws 409 "A user with this email already exists" on a public, security('none') route — a direct enumeration oracle. Return a generic success + "you already have an account" email, or document the tradeoff.

3. What the roadmap got right (verified)

Credit where due — these claims hold up under direct inspection:

  • ✓ Default-deny fails closed. enforceFortressPermission ends with throw Errors.forbidden('No permission mapping for this route'); no-metadata routes are denied.
  • ✓ API-key scope intersection is correct. withinCredentialScope AND-gates the IAM result; null=unscoped, []=deny-all, * and resource:* handled.
  • ✓ API keys cannot self-manage API keys — enforced at the service method (resolveCallerSubject throws for any scopes !== undefined), not just HTTP.
  • ✓ Impersonation is service-level gated — short-lived default, no refresh token, RFC 8693 act claim.
  • ✓ OAuth refresh rotation is genuinely good: transactional CAS on usedAt isNull, family revocation on replay, scope-narrowing-only.
  • ✓ redirect_uri exact match with a correct RFC 8252 loopback carve-out; mix-up iss (RFC 9207) present; plain PKCE rejected; secrets compared with timingSafeEqualHex.
  • ✓ Argon2id with sound parameters (64 MB, t=3), constant-time verify.
  • ✓ Route matching is segment-exact with no traversal / trailing-slash / case bypass found.
  • ✓ Binding partial-unique indexes for nullable tenantId are correct (the plain unique() is redundant but harmless).

5. Suggested priority order

  1. C1–C3, H1–H4 — the load-bearing security defects. Until fixed, mark tenancy and data-isolation "experimental / not production-ready" and document that rotation guarantees require Postgres.
  2. H5–H8 — CSRF wiring, OAuth consent ownership, PKCE enforcement, enumeration.
  3. M1–M2 — unawaited validatePassword (silently saves weak passwords) and reserved-claim/act injection are quick, high-value fixes.
  4. M3–M12, Low — hardening pass.
  5. Add the regression tests the roadmap already lists (concurrency, malicious tenant codes), plus new ones for H1 / H4 / H6.

The roadmap's later phases (threat model, migrations, external review) remain the right direction — but the "Phase 1 mostly complete" framing should be revised: several Phase-1 guarantees don't hold yet.
