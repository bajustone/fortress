1 · Reading this document

Audit → compliance plan, one-to-one

The audit produced 19 findings. This document keeps the same numbering (§4.1 through §4.11, plus the §3 "what's right" items as keep-as-is) so every audit row maps to exactly one compliance entry. Each entry has four parts:

  • Spec clause — the canonical text we must satisfy (RFC §, OIDC §, BCP §).
  • Observable behaviour — what an external RP / scanner sees on the wire when fortress is compliant.
  • Code shape — the smallest concrete change in src/plugins/oauth/ (and elsewhere) that produces it.
  • Definition of done — the exact acceptance criteria, including the test that proves it.
Scope discipline. "Fully comply" here means: every audit finding moves to PASS on the matrix. It does not mean implementing every OAuth/OIDC extension that exists (DPoP, PAR, CIBA, mTLS, token exchange, dynamic client registration). Those remain non-goals until a real RP needs them.

Definition of "fully comply": every row of the audit's §5 compliance matrix is PASS, the userinfo response is OIDC-shaped without the TDMP override, and the discovery document is RFC 8414 + OIDC Discovery 1.0 valid by an external validator (e.g. openid-client's discovery autoconfig succeeds and a Moodle / Keycloak federation flow round-trips end-to-end against an unmodified fortress instance).

Out of scope (explicit non-goals): RFC 8628 device flow, RFC 8693 token exchange, RFC 8705 mTLS, RFC 9126 PAR, RFC 9449 DPoP, dynamic client registration. These can be future plugins or sub-modules; nothing in this plan assumes them.

3 · What stays as-is

Audit §3 items already at PASS — guard against regression

The audit's §3 confirmed ten primitives that are already correct. Compliance requires that they remain correct after the §4 changes:

  • Authorization-code primitives: 256-bit codes, single-use via usedAt, hashed at rest, bound to client + redirect URI, ≤600 s lifetime.
  • Exact-match redirect-URI validation (no wildcards, no prefix matching) — must survive the RFC 8252 loopback addition (§4.8).
  • S256 PKCE derivation; the plain method must continue to be rejected.
  • Hashed-at-rest secrets, codes, and access tokens — the constant-time fix in §4.4 must not regress this.
  • RFC 7662 introspection shape ({active:false} on miss; client-auth required).
  • RFC 7009 revocation always-OK semantics.
  • Pending-flow / identity-broker pattern.
  • Code-replay rejection on second exchange.
  • RFC 6750 bearer-token parsing on userinfo.

Each of these gets at least one regression test added alongside the new feature tests so the §4 changes can't silently break them.

4.1 · OIDC-shaped userinfo response HIGH audit §4.1

OIDC Core 1.0 §5.3 · §5.1

Spec clause. §5.3: the userinfo endpoint MUST return claims as a JSON object with content-type application/json; sub MUST be present and MUST equal the sub the access token was issued for; standard claims MUST follow §5.1 names and types (email:string, email_verified:boolean, name:string, given_name/family_name:string, preferred_username:string, updated_at:Unix-seconds number). Unknown / unsupported claims MUST be omitted, not nulled.

Observable behaviour. A request GET /oauth/userinfo with a valid bearer returns:

{
  "sub": "42",
  "email": "alice@example.com",
  "email_verified": true,
  "name": "Alice Example",
  "preferred_username": "alice@example.com",
  "updated_at": 1714867200
}

No id, isActive, createdAt, or passwordHash-adjacent fields. sub is always a string.

Code shape. Replace handleUserInfoRequest's body in src/plugins/oauth/index.ts:850-852 with a mapping function toOidcUserinfo(user, scope) that:

  • Stringifies user.id as sub.
  • Includes email/email_verified only if the access token's scope contains email (or openid as a permissive default until §4.9 lands).
  • Includes name/preferred_username only if scope contains profile.
  • Converts updatedAt to Math.floor(new Date(updatedAt).getTime() / 1000).
  • Allows host apps to extend via a new OAuthConfig.userinfoClaims?: (user, scope) => Record<string,unknown> hook (replaces the TDMP override at the right seam).
Definition of done
  • Stock fortress (no overrides) returns the OIDC-shaped JSON above for the test user.
  • Test asserts: sub is a string, updated_at is a number, no DB-internal field names leak.
  • Moodle core\oauth2\client::get_userinfo() end-to-end works without the TDMP override (validated via the e2e harness in /Users/bajustone/dev/rtb/tdmp/oauth-e2e-test/).

4.2 · Issue id_token on the openid scope MED audit §4.2

OIDC Core 1.0 §3.1.3.7 · §2 · OIDC Discovery §3

Spec clause. §3.1.3.7: when the request includes scope=openid, the token response MUST include id_token in addition to access_token. The id_token is a signed JWT with at least iss, sub, aud (= client_id), exp, iat; nonce MUST be echoed if present in the authorization request; auth_time SHOULD be present if max_age was requested. The alg in the JOSE header MUST match one of id_token_signing_alg_values_supported; RS256 is the OIDC default. The signing key MUST be discoverable via jwks_uri (RFC 7517).

Observable behaviour. A POST to /oauth/token with grant_type=authorization_code for a code minted from an authorize request that included scope=openid returns:

{
  "access_token": "...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "id_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6Ii4uLiJ9...",
  "scope": "openid email"
}

Code shape.

  • New file src/plugins/oauth/jwks.ts — RS256 keypair generation via jose.generateKeyPair('RS256'), JWK export, kid derived from RFC 7638 thumbprint, persisted via a new model oauth_signing_key (id, kid, alg, public_jwk, private_jwk, created_at, rotated_at). One active key + a grace window for rotation.
  • New file src/plugins/oauth/id-token.ts — issueIdToken({user, clientId, nonce, authTime, scope, issuerUrl}): builds claims, signs with the active key, returns the compact JWS.
  • New endpoint GET /oauth/.well-known/jwks.json — returns { keys: [publicJwkOfActiveKey, ...gracePublicJwks] }; cache-control public, max-age=300.
  • Discovery additions: jwks_uri, id_token_signing_alg_values_supported: ["RS256"], claims_supported.
  • Authorize handler: persist nonce on the auth code (new column) when present; token handler: read it back and pass to issueIdToken.
  • Pending-flow + auth-code records: track auth_time (login timestamp from the session) for correct auth_time claim.
Definition of done
  • openid-client (Node) auto-discovers fortress and validates the id_token signature against jwks_uri with no manual config.
  • Test: id_token aud equals the requesting client_id; nonce is echoed when supplied; iss matches discovery issuer exactly.
  • JWKS rotation test: rotating keys keeps an old kid verifying for a configurable grace window; new tokens use the new kid.
  • Discovery's response_types_supported stays ["code"] (not "id_token" directly — we only issue id_token via the code grant).

4.3 · Refresh-token grant with rotation MED audit §4.3

RFC 6749 §6 · RFC 9700 §2.2.2

Spec clause. RFC 6749 §6: the AS issues an optional refresh_token alongside access_token; grant_type=refresh_token + refresh_token=<value> mints a new access token. RFC 9700 §2.2.2: refresh tokens for public clients MUST be sender-constrained or rotated; rotation means the AS issues a new refresh token at every use and treats reuse of an already-rotated token as an attack — the entire token family MUST be invalidated.

Observable behaviour.

POST /oauth/token
grant_type=refresh_token&refresh_token=R1&client_id=...&client_secret=...

→ 200 OK
{ "access_token":"A2", "refresh_token":"R2", "token_type":"Bearer",
  "expires_in":3600, "scope":"openid email" }

# Replay of R1 after R2 was issued:
POST /oauth/token grant_type=refresh_token&refresh_token=R1
→ 400 { "error":"invalid_grant", "error_description":"refresh token reuse detected" }
# AND: R2 is now revoked, family is dead.

Code shape. Reuse the existing core machinery — src/core/auth/refresh-token.ts already provides generateRefreshToken, family rotation, and reuse detection for the user-session refresh flow. Add an OAuth-scoped wrapper:

  • New model oauth_refresh_token (token_hash, family_id, client_id, user_id, scope, issued_at, expires_at, used_at, parent_id).
  • New method handleRefreshGrant(clientId, clientSecret, refreshToken): validate client → look up by hash → if used_at set, delete the entire family + audit-log TOKEN_REUSE_DETECTED + return invalid_grant → otherwise mark used_at, mint new access token + new refresh token in same family, return both.
  • Discovery: add "refresh_token" to grant_types_supported.
  • Token endpoint dispatcher: route grant_type=refresh_token.
  • Default refresh-token lifetime: 30 d sliding (configurable via OAuthConfig.refreshTokenExpirySeconds); access-token lifetime stays 1 h.
Definition of done
  • Happy-path: refresh returns a new pair, old refresh is invalidated, new access verifies against introspection.
  • Replay-detection test: replaying R1 after R2 was issued returns invalid_grant AND R2 is also revoked.
  • Family-revocation event reaches the existing addAuthObserver stream as TOKEN_REUSE_DETECTED.
  • Confidential-client refresh requires client_secret; public-client refresh (post §4.8) requires the original PKCE-bound client_id.

4.4 · Constant-time secret comparison MED audit §4.4

RFC 9700 §2.1.1 · OWASP ASVS V2.4

Spec clause. "Implementations MUST use a constant-time comparison routine when comparing secrets" (paraphrased; the canonical guidance lives in OWASP ASVS V2.4 and timing-attack literature). === on hex strings is an early-exit comparison.

Observable behaviour. Untestable from the wire — this is a code-quality gate. Static review confirms no remaining hashToken(...) === storedHash or a === b on secret-derived material.

Code shape. Add a small util src/core/auth/timing-safe.ts:

export function timingSafeEqualHex(a: string, b: string): boolean {
  if (a.length !== b.length) return false;
  // Length-prefix is fine because both sides are SHA-256 hex (always 64 chars).
  let diff = 0;
  for (let i = 0; i < a.length; i++) diff |= a.charCodeAt(i) ^ b.charCodeAt(i);
  return diff === 0;
}

Replace the three call sites in src/plugins/oauth/index.ts (client secret check, code hash check, access-token hash check) and any equivalent in core auth.

Definition of done
  • grep -n '=== storedHash\|=== hashedCode\|=== hashedToken' src/ returns nothing.
  • Lint rule (or unit test on the source string) blocks regression: any new storedHash reference must go through timingSafeEqualHex.

4.5 · Mandatory PKCE on /oauth/authorize HIGH audit §4.5

RFC 9700 §2.1.1 · §4.5.3.2 · RFC 7636

Spec clause. RFC 9700 §2.1.1: "Clients MUST use PKCE [RFC 7636] for the OAuth authorization code grant." Authorization servers MUST require PKCE for all clients (with a narrow exception for confidential clients using sender-constrained tokens, which fortress doesn't issue today).

Observable behaviour.

GET /oauth/authorize?response_type=code&client_id=...&redirect_uri=...&state=...
→ 302 with error redirect:
  <redirect_uri>?error=invalid_request&error_description=code_challenge%20required&state=...

# With PKCE:
GET /oauth/authorize?...&code_challenge=ABC&code_challenge_method=S256
→ 302 to loginUrl/consentUrl as today.

Code shape. In handleAuthorizeRequest (around src/plugins/oauth/index.ts:616), reject the request when codeChallenge is missing:

if (!codeChallenge) {
  throw Errors.badRequest('code_challenge is required (PKCE)');
  // Mapped by the dispatcher to a 302 redirect with
  // error=invalid_request per RFC 6749 §4.1.2.1.
}
if (codeChallengeMethod !== 'S256') {
  throw Errors.badRequest('Only S256 code_challenge_method is supported');
}

The existing dispatcher path that converts FortressError into a redirect-with-error (per RFC 6749 §4.1.2.1) handles the rest. Confidential-client carve-out: an explicit OAuthConfig.allowNonPkceConfidentialClients?: boolean escape hatch (default false) is added for legacy server-side RPs, but the sample config and docs make clear it's discouraged.

Definition of done
  • An authorize request without code_challenge redirects with error=invalid_request; state is echoed.
  • Discovery still advertises code_challenge_methods_supported: ["S256"] only.
  • Test: tampering with the verifier at exchange time returns invalid_grant (the existing PKCE-correctness test continues to pass).

4.6 · RFC 9207 iss in the authorization response HIGH audit §4.6

RFC 9207 · RFC 9700 §4.4

Spec clause. RFC 9207 §2: the AS MUST add an iss parameter to the authorization response, set to the AS's issuer URL (same value as discovery's issuer). RFC 9207 §3: the AS metadata MUST include authorization_response_iss_parameter_supported: true. Defends against the mix-up attack of RFC 9700 §4.4.

Observable behaviour.

GET /oauth/authorize?...   # success
→ 302 Location: https://rp.example/cb?code=...&state=...&iss=https%3A%2F%2Fas.example%2Fapi%2Fv1

GET /.well-known/oauth-authorization-server
→ { ..., "authorization_response_iss_parameter_supported": true, ... }

Code shape. Wherever the success redirect is built (consent-approve handler in src/plugins/oauth/index.ts), append iss=<encodeURIComponent(issuerUrl)> to the query. Add the metadata flag in handleDiscovery(). The issuerUrl string used MUST be byte-identical to the one in discovery.

Definition of done
  • Every success redirect contains iss= with URL-encoded issuer.
  • Error redirects (per RFC 6749 §4.1.2.1) also include iss — RFC 9207 §2 requires it on all responses, success or error.
  • Discovery flag set; openid-client with checks: ['iss'] validates the response cleanly.

4.7 · Discovery-document completeness MED audit §4.7

RFC 8414 §2 · OIDC Discovery §3

Spec clause. RFC 8414 §2 enumerates a long list of metadata fields, most marked OPTIONAL but several effectively required for interop. OIDC Discovery §3 adds jwks_uri (REQUIRED), claims_supported (RECOMMENDED), id_token_signing_alg_values_supported (REQUIRED if id_tokens are issued).

Observable behaviour. The discovery document gains:

{
  ...existing fields...,
  "jwks_uri": "https://as.example/api/v1/oauth/.well-known/jwks.json",
  "scopes_supported": ["openid","email","profile", ...host-app scopes],
  "claims_supported": ["sub","email","email_verified","name","preferred_username","updated_at","iss","aud","exp","iat","auth_time","nonce"],
  "response_modes_supported": ["query"],
  "id_token_signing_alg_values_supported": ["RS256"],
  "authorization_response_iss_parameter_supported": true,
  "grant_types_supported": ["authorization_code","client_credentials","refresh_token"]
}

Code shape. Extend the literal in handleDiscovery() (~line 865). scopes_supported is sourced from the union of the keys in OAuthConfig.scopePermissionMap ∪ {openid, email, profile}.

Definition of done
  • Discovery passes openid-client's validator and a third-party scanner (e.g. mitreid openid-conformance-suite "discovery" profile).
  • JSON Schema test in oauth.test.ts asserts presence and types of every field above.

4.8 · Public-client mode + RFC 8252 loopback redirects MED audit §4.8

RFC 6749 §2.1 · RFC 8252 §7.3 · §8.4

Spec clause. RFC 6749 §2.1 distinguishes confidential vs. public clients. Public clients (SPAs, native apps) authenticate the token endpoint by presenting only their client_id + PKCE (no secret). RFC 8252 §7.3: native apps SHOULD use loopback redirects http://127.0.0.1:<port>/<path>; §8.4: the AS MUST permit any port on a registered http://127.0.0.1/... redirect (the port is chosen at runtime by the OS).

Observable behaviour.

  • Client registration accepts tokenEndpointAuthMethod: 'none'; if set, no secret is generated and the token endpoint accepts the client without client_secret as long as PKCE verifies.
  • Registered redirect http://127.0.0.1/cb matches inbound http://127.0.0.1:53127/cb. Same for [::1]. localhost (DNS) is not auto-flexible — RFC 8252 §8.3 prefers literal loopback IPs.
  • Discovery exposes token_endpoint_auth_methods_supported: ["client_secret_basic","client_secret_post","none"].

Code shape.

  • Schema: add tokenEndpointAuthMethod column on oauth_client (default 'client_secret_basic').
  • Authenticator: short-circuit secret check when method is 'none'; require PKCE.
  • Redirect matcher: extend exact-match with a loopback rule — if registered URI's host is 127.0.0.1 or [::1] and inbound URI matches the registered URI in scheme + host + path + query, allow any port.
Definition of done
  • Public-client end-to-end test: register with tokenEndpointAuthMethod:'none'; full code+PKCE flow succeeds without a secret; secret-using token call returns invalid_client.
  • Loopback test: registered http://127.0.0.1/cb matches inbound http://127.0.0.1:53127/cb; mismatched path or scheme is still rejected.
  • Wildcard hostnames remain rejected (no general loopback "any port" loosening for non-loopback hosts).

4.9 · Per-client scope allow-list with intersection MED audit §4.9

RFC 6749 §3.3 · RFC 9700 §2.2.1

Spec clause. RFC 6749 §3.3: the AS MAY fully ignore the requested scope or issue a different scope; if so, the response MUST include the actual scope. The implicit invariant is that the AS — not the client — controls what scopes a token bears. RFC 9700 §2.2.1 frames over-broad scope as an exfil vector and recommends server-side enforcement.

Observable behaviour.

# Client registered with allowedScopes = ["openid","email","profile"]
GET /oauth/authorize?...&scope=openid+email+admin:write
→ Authorize with effective scope = "openid email" (admin:write dropped silently
  per §3.3) OR rejected with error=invalid_scope when the intersection is empty.
Token response & introspection both report scope = "openid email".

Code shape.

  • Schema: oauth_client.allowedScopes JSON column.
  • Authorize handler: effectiveScope = intersect(requestedScope, client.allowedScopes); if empty, redirect with error=invalid_scope.
  • Persist effectiveScope on the auth code; token + id_token + introspection all return the effective scope.
  • If allowedScopes is null (legacy / unset), behave as today (pass through) — preserves backwards compat for v0 consumers, with a deprecation warning logged on first use.
Definition of done
  • Test: client allowed ["openid","email"] requesting "openid email admin" gets a token bearing scope="openid email"; introspection agrees.
  • Test: empty intersection → redirect with error=invalid_scope.
  • Default-deny on admin:* for the seeded admin plugin client until explicitly granted.

4.10 · Standard RFC 6749 §5.2 error codes LOW audit §4.10

RFC 6749 §5.2 · §4.1.2.1

Spec clause. §5.2 lists the canonical machine-readable error codes for token-endpoint failures: invalid_request, invalid_client, invalid_grant, unauthorized_client, unsupported_grant_type, invalid_scope. §4.1.2.1 lists the analogous codes for authorize-redirect failures (access_denied, server_error, temporarily_unavailable, …). The error field MUST be one of these enumerated codes; error_description carries the human text.

Observable behaviour.

HTTP/1.1 400 Bad Request
Content-Type: application/json
{
  "error": "invalid_grant",
  "error_description": "Authorization code expired"
}

Code shape. Introduce OAuthError (extends FortressError) with the enum codes; replace each Errors.badRequest('human') in src/plugins/oauth/index.ts with OAuthError.invalidGrant('human') etc. The HTTP error mapper in src/core/http/error-response.ts serialises OAuthError to {error, error_description}.

Definition of done
  • Every OAuth-endpoint failure path in oauth.test.ts asserts a specific error code from the §5.2/§4.1.2.1 set.
  • No OAuth endpoint can return a JSON body with a free-form error string.

4.11 · HTTPS issuer assertion at startup LOW audit §4.11

RFC 8414 §2 · RFC 9700 §4.16

Spec clause. RFC 8414 §2: "The authorization server's issuer identifier… MUST be a URL that uses the 'https' scheme". RFC 9700 §4.16 reinforces: production deployments MUST use TLS for all OAuth endpoints.

Observable behaviour. When NODE_ENV is 'production' and OAuthConfig.issuerUrl is non-HTTPS, fortress refuses to start with a clear error. Dev / test mode keeps the existing localhost-HTTP behaviour.

Code shape. In the OAuth plugin's init hook (or wherever issuerUrl is resolved):

if (process.env.NODE_ENV === 'production' &&
    !issuerUrl.startsWith('https://')) {
  throw new Error(
    `[fortress/oauth] issuerUrl must use https:// in production (got: ${issuerUrl})`
  );
}
Definition of done
  • Unit test: NODE_ENV=production + issuerUrl='http://...' → init throws.
  • Same with https:// → init succeeds.
  • Dev mode (NODE_ENV !== 'production') with HTTP issuer → init succeeds, with a single logger.warn.

6 · Test strategy

How a reviewer can verify "fully complies"

Unit

  • src/plugins/oauth/oauth.test.ts grows with one describe() per audit finding (§4.1 … §4.11).
  • Each describe block contains: a happy-path test, a negative test (the attack the spec defends against), and a discovery-document assertion where relevant.
  • Constant-time compare (§4.4) gets a string-search test on the source so accidental === regressions fail CI.

Integration

  • The TDMP e2e harness at /Users/bajustone/dev/rtb/tdmp/oauth-e2e-test/ runs against unmodified fortress (no override) and Moodle's core\oauth2\client reaches "logged in" without TDMP-specific patches.
  • An openid-client (Node) auto-discovery + code+PKCE flow validates: id_token signature via JWKS, iss on the authz redirect, refresh-token rotation, replay-detection.

Conformance

  • Stretch goal — run the OpenID Foundation conformance suite ("basic OP" profile) against fortress; treat failures as new audit items, not as soft regressions.
