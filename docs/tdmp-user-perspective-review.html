Fortress Library Review — TDMP User Perspective

Review date: 2026-06-05 · Package reviewed: @bajustone/fortress@0.1.1 · Context: TDMP backend integration

Honest verdict: Fortress is a useful and promising auth/IAM foundation, but it is not yet a mature black-box security dependency. TDMP benefits from it, but also relies on local wrappers, route-map generation, seed scripts, and workarounds that reveal sharp edges in the library.

Scope reviewed

  • TDMP usage: src/fortress.ts, src/server.ts, src/modules/auth, src/modules/oauth, src/modules/users, scripts/seed-auth.ts, route map, Fortress schema re-exports, and auth architecture docs.
  • Fortress source/docs: README, SECURITY, CHANGELOG, core auth/IAM, Hono adapter, Drizzle adapter/schema, admin/API-key/OAuth/OpenAPI plugins.

What Fortress does well

  • Coherent unified model: auth, IAM, plugin routes, endpoint metadata, validation, OpenAPI, and Hono integration share one model.
  • Good primitives: Argon2id hashing, JWT secret length enforcement, refresh token rotation/reuse detection, service-account subjects, API keys, and OIDC/OAuth features.
  • Adapter-based design: TDMP cleanly plugs Postgres/Drizzle into Fortress and re-exports Fortress tables for migrations.
  • Useful subject model: USER and SERVICE_ACCOUNT are first-class IAM subjects, which is valuable for TDMP service-to-service flows.
  • OpenAPI route metadata: TDMP uses endpoint declarations to generate route maps and seed permissions, which is productive.
  • Observability: pluggable logger, auth/IAM observers, and OTel hooks are thoughtfully designed.

Major findings

SeverityFindingWhy it mattersRecommendation
High API-key scopes appear stored but not enforced by RBAC. The plugin resolves an API key to its owning subject; later checks use the subject's IAM permissions, not the key's scopes. A supposedly narrow key may inherit broad subject permissions. Thread resolved key scopes into principal/claims and intersect them in RBAC permission checks.
High Built-in impersonation endpoint lacks explicit fortress:impersonate permission. The service warns callers to check permission, but the core endpoint is bearer-only. TDMP's custom route is route-map protected, but the library endpoint is risky if mounted. Add .permission('fortress', 'impersonate') to the built-in endpoint or disable/shadow it until fixed.
High Refresh rotation is not atomic. Parallel refreshes can race between lookup and revocation, potentially minting multiple valid descendants. Wrap refresh rotation in a transaction with row locking or an atomic conditional update.
Medium IAM permission model has correctness gaps. findOrCreatePermission keys by resource/action only, ignoring effect/conditions; cache invalidation is uneven; role bindings lack uniqueness. Make permission identity include effect/condition semantics or explicitly document limitations; add constraints and consistent cache invalidation.
Medium Drizzle adapter does not expose rawQuery. Fortress contains an optimized IAM query path, but the default Drizzle adapter falls back to multiple queries per check. Add dialect-aware rawQuery or optimized adapter methods for permission resolution.
Medium OAuth is feature-rich but recently unstable. Changelog shows recent regressions around /oauth/* security handling. Current implementation is ambitious and should be tested against each RP. Add conformance/integration tests for Moodle/openid-client and verify every grant/consent/userinfo path.
Medium Docs overstate maturity in places. README claims comprehensive features; SECURITY.md supported versions say 0.0.x while package is 0.1.1; published package excludes linked docs. Tighten docs to match current guarantees and publish referenced docs.

TDMP integration assessment

TDMP uses Fortress effectively, but the integration is layered and somewhat fragile:

  • src/fortress.ts configures Fortress with Drizzle, JWT, OAuth, admin, API-key, and OpenAPI plugins.
  • src/server.ts applies TDMP global auth/RBAC middleware and then mounts Fortress routes under /api/v1.
  • TDMP defines its own auth routes that call Fortress services directly, while Fortress also has built-in auth/admin/IAM routes.
  • TDMP generates a route map from OpenAPI and seeds role permissions from that route map.

This gives TDMP control, but also creates risk of route shadowing, mismatched public/protected routes, and duplicate policy layers.

TDMP-specific notes

  • OAuth consent route RBAC may be wrong: generated route map includes /oauth/flows/:flowId, approve, and deny. Normal users may not have these permissions, which can block user consent unless explicitly seeded.
  • Stale architecture docs: docs/architecture/auth-flow.md describes Azure AD login and refresh cookies, while current implementation is Fortress credential login plus TDMP as an OAuth/OIDC provider.
  • Seed script compensates for library gaps: it directly queries Fortress tables and pre-checks role bindings because duplicates are otherwise possible.
  • Custom OAuth claim hook is reasonable: TDMP's userinfoClaims split of name into given_name/family_name is a good local adaptation.

Final recommendation

Continue using Fortress in TDMP, but treat it as an internal platform component that TDMP hardens and tests, not as a fully mature external security product. The design direction is good and the integration payoff is real, but pre-1.0 auth libraries need skepticism: pin versions, read changelogs, run regression tests, and maintain local compensating controls around every sensitive flow.
